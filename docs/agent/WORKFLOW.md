# 에이전트 협업 방식

## 구현 순서와 범위

- 새 기능의 구현 순서를 요청받으면 번호를 붙여 설명한다. 단계마다 구현 범위와 사용자가 직접 확인할 수 있는 동작을 적는다.
- UI, 사용자 입력, 실제 처리 로직을 각각 확인할 수 있도록 나눈다. 예를 들어 영상 선택은 화면 배치, 버튼을 통한 파일 선택, 드래그 앤 드롭, 로컬 재생 순으로 나눌 수 있다.
- 사용자가 번호를 지정하면 직전에 합의한 계획에서 해당 단계만 구현한다. 여러 단계를 같이 해 달라고 하면 지정된 범위에서 묶는다.
- 코드 설명이나 구조 검토를 요청받으면 먼저 질문에 답한다. 별도 구현이나 큰 구조 변경은 요청받은 작업 범위에 맞춰 진행한다.

## 코드 구조와 주석

- 여러 화면에 쓰이는 버튼과 레이아웃은 기존 공용 컴포넌트와 스타일을 재사용한다. UI를 바꿀 때는 공용 스타일로 해결할 수 있는지 먼저 확인한다.
- 파일 선택, 플레이어, 편집 패널처럼 역할이 다른 코드는 독립적으로 읽고 검수할 수 있게 나눈다. 코드 분할 단계에서는 기존 동작을 기준으로 검증한다.
- 이벤트 핸들러, `useEffect`, 정리 함수에는 실행 이유나 놓치기 쉬운 동작을 짧게 주석으로 남긴다. 페이지나 레이아웃 선언 위에 역할을 반복하는 주석은 생략한다.

## 설명과 검수

- 코드에 대한 질문은 사용자가 선택한 줄이나 함수부터 설명한다. 어떤 이벤트가 실행을 시작하고, 어떤 함수가 호출되고, 화면에 무엇이 바뀌는지 순서대로 짚는다.
- 브라우저나 React가 제공하는 동작과 프로젝트 코드가 담당하는 동작을 구분해 설명한다. 예를 들어 파일 선택 버튼은 숨겨진 파일 입력 요소를 클릭하고, 파일을 실제로 선택하면 브라우저가 `change` 이벤트를 발생시킨다.
- 구현 후에는 확인한 빌드·린트·브라우저 동작과 아직 확인하지 못한 부분을 알린다. 화면에만 배치한 버튼이나 아직 연결하지 않은 저장 기능은 현재 동작 범위를 명시한다.

## 커밋, PR과 복원

- 구현한 단계는 사용자가 검수할 수 있게 작업 트리에 남긴다. 커밋과 PR은 각각 요청받았을 때 [커밋 및 PR 작성 규칙](COMMIT_AND_PR.md)에 따라 진행한다.
- 브랜치 생성을 요청받으면 기준 브랜치와 새 브랜치 이름을 확인해 알린다. PR에 이전 작업 커밋이 함께 포함되면 그 범위를 설명한다.
- 커밋만 되돌려 달라는 요청에서는 작업 파일을 보존한다. 구현을 되돌린 후 작은 단위로 다시 진행하는 경우에는 기존 변경을 Git에서 복원할 수 있게 보존하고, 백업 위치와 돌아간 기준을 알린다.
